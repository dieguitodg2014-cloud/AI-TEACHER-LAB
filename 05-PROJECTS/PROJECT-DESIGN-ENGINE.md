# PROJECT DESIGN ENGINE

## Version
1.0

## Purpose

The Project Design Engine extends AI TEACHER LAB from individual lessons to coherent instructional projects, courses, modules, units, camps, vacation programs, workshops, and multi-session learning experiences.

A project is not a collection of lessons. It is a connected learning system in which each component contributes to defined outcomes.

## Core Principle

**Design the whole learning journey before optimizing individual lessons.**

The system must preserve alignment across:

**Needs → Outcomes → Sequence → Learning Experiences → Evidence → Assessment → Review**

## Project Types

The engine may design:

- complete ESL courses
- modules
- units
- short intensive programs
- vacation courses
- camps
- workshops
- special projects
- thematic sequences
- exam preparation programs
- teacher-development projects
- family/community language events

The pedagogical framework remains stable while the structure, duration, audience, and deliverables change.

## Project Intake

Before designing a project, identify:

1. target learners
2. proficiency level or range
3. age and learner profile
4. context
5. duration
6. frequency
7. session length
8. institutional constraints
9. available resources
10. desired outcomes
11. assessment requirements
12. communicative needs
13. special events or milestones
14. required deliverables

If essential information is missing, the Director Pedagógico may make conservative assumptions only when doing so does not create a pedagogical risk. Otherwise, clarification is required.

## Backward Design at Project Level

The project begins with the final intended learning results.

### Stage 1 - Desired Results

Define:
- final competencies
- communicative abilities
- language outcomes
- functional outcomes
- learner autonomy expectations

### Stage 2 - Evidence

Determine how learners will demonstrate achievement.

Evidence may include:
- performance tasks
- practical demonstrations
- conversations
- presentations
- projects
- written products
- integrated-skills assessments

### Stage 3 - Learning Plan

Only after outcomes and evidence are defined should the system determine:
- modules
- units
- lessons
- practice sequences
- materials
- projects

## Project Architecture

A project should normally have these layers:

**Program → Modules → Units → Lessons → Activities → Evidence**

Not every project requires every layer. The architecture should expand or contract according to scope.

## Sequencing Principles

The engine must consider:

- prerequisite knowledge
- language progression
- skill progression
- communicative progression
- cognitive progression
- recycling
- retrieval and consolidation
- increasing independence
- assessment points

New language should not be introduced simply because it appears on a grammar list. It must have a pedagogical and communicative reason.

## Spiral Learning

Important language and skills should be recycled across the project.

Recycling should normally change the context, communicative purpose, cognitive demand, or interaction rather than repeating identical exercises.

## Progression

Across a project, progression may occur through:

- greater language range
- greater accuracy
- longer output
- more complex relationships between ideas
- reduced scaffolding
- greater learner autonomy
- more authentic interaction
- broader contexts
- more demanding cognitive processes

The Level Control Engine remains responsible for proficiency-level progression.

## Session Architecture

Individual lessons are generated by the ESL Lesson Engine and must remain connected to the project sequence.

Every lesson in a project should answer:

- What has already been learned?
- What is being learned now?
- Why is it being learned now?
- What will learners need next?
- How does today's evidence inform the next lesson?

## Project Milestones

Longer projects should include deliberate milestones such as:

- diagnostic point
- consolidation point
- formative checkpoint
- performance task
- mid-course review
- final performance
- final assessment

Milestones must have a pedagogical purpose rather than exist only for administrative convenience.

## Assessment Architecture

Assessment should be distributed across the project.

A project may include:

- entry diagnostic
- ongoing formative evidence
- unit checks
- integrated performance tasks
- mid-course assessment
- final performance or examination

The Assessment Engine defines assessment quality and criteria.

## Project Coherence Check

The Quality Control Engine must verify:

1. The project outcomes are realistic.
2. The sequence supports those outcomes.
3. Prerequisites are respected.
4. Lessons build on previous learning.
5. Important language is recycled.
6. Assessment is aligned with outcomes.
7. The workload is realistic.
8. Timing is mathematically consistent.
9. The project does not overload learners with unnecessary grammar.
10. Activities serve the stated purpose.
11. Milestones provide useful evidence.
12. The final experience reflects the learning journey.

## Time and Feasibility

Project planning must calculate actual instructional time.

The engine must distinguish between:
- contact hours
- instructional days
- weekends
- holidays
- assessment days
- special events
- preparation or transition time

If the available time cannot realistically support the requested outcomes, the system must flag the conflict rather than silently compressing the curriculum.

## Learner Experience

Projects should feel like coherent learning experiences rather than disconnected worksheets.

Where appropriate, projects should include:
- meaningful themes
- recurring contexts
- learner choice
- collaboration
- real-world purposes
- visible progress
- practical outcomes

For children, play, movement, songs, stories, technology, challenges, and creative production may be integrated when pedagogically appropriate.

For adults, the project should respect adult identity, experience, autonomy, and real-life communication needs. It must not become infantilized simply because it is interactive.

## Project Deliverables

Depending on the request, the engine may produce:

- project brief
- mission and vision
- objectives
- curriculum map
- module sequence
- unit plans
- lesson sequence
- assessment plan
- materials plan
- teacher guide
- learner materials
- final project
- presentation materials
- implementation notes

## Project Change Management

When a project changes, the engine must evaluate the effect of the change on:

- objectives
- sequence
- timing
- assessment
- materials
- dependencies
- workload

A local change must not silently break the rest of the project.

## AI Tool Coordination

Secondary AI tools may be assigned production tasks such as:
- visual generation
- slide design
- audio generation
- formatting
- document production
- media adaptation

They must not independently redefine:
- learning objectives
- level
- assessment construct
- pedagogical sequence
- communicative purpose

Those decisions remain under the Master System and Director Pedagógico.

## Project Review Cycle

For longer projects, the system should use:

**Design → Build → Review → Pilot/Implement → Collect Evidence → Adjust → Rebuild**

Changes should be evidence-based whenever actual learner performance is available.

## Final Project Approval Gate

Before a project is considered classroom-ready, verify:

- outcomes are clear
- level is controlled
- sequence is coherent
- lessons are connected
- assessment is aligned
- timing is realistic
- materials are feasible
- workload is appropriate
- learner experience is meaningful
- quality-control requirements are satisfied

## System Priority

The Project Design Engine is subordinate to the Master System and coordinates with the Level Control Engine, ESL Lesson Engine, Assessment Engine, Quality Control Engine, and AI Tool Coordination system.

Its purpose is to ensure that AI TEACHER LAB can design not only excellent lessons, but coherent learning journeys over time.
